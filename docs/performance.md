# web/ 技術検証: データ量とパフォーマンスの計測結果

`web/`（DuckDB-WASM + Mosaic/vgplot によるブラウザ内完結版の技術検証）で、
データ量を増やしたときにどこで実用に耐えなくなるかを計測した記録。

## 測定条件

- **対象**: `web/src/main.ts`。`?n=<行数>&mark=<dot|raster|hexbin>` で
  行数とマーク種別を切り替えられるようにした最小構成（専用UIは無し）。
- **ブラウザ**: Playwright 1.63.0 が管理するヘッドレス Chromium
  153.0.8010.12（macOS上）。
- **計測方法**: 行数・マーク種別の組み合わせごとに `chromium.launch()` で
  ブラウザを新規起動し、ページを開いて計測した。ブラウザは毎回まっさらな
  プロファイルで起動するため、DuckDB-WASM 本体は毎回 jsDelivr から
  フェッチし直している（ブラウザキャッシュの効果は含んでいない）。
- **計測項目と取得方法**:
  - CSV生成（JS側、参考値）・DuckDB-WASMへの登録・初回描画の所要時間:
    ページ内で `performance.now()` により計測し `window.__metrics` に格納。
  - ドラッグ選択への応答時間: Playwright でマウスのドラッグ操作を発行し、
    選択結果が `window.__metrics.lastSelectionAppliedAt` に反映されるまでの
    時間を計測。ドラッグ開始・反映完了のどちらもページ内の
    `performance.now()` で揃えている（driver側とページ側で時計がずれるため、
    片方だけ別の時計を使うと誤差になる）。
  - DOMノード数・メモリ使用量: Chrome DevTools Protocol の
    `Performance.getMetrics` が返す `Nodes` と `JSHeapUsedSize`。

### なぜ `performance.memory.usedJSHeapSize` ではなく CDP の `JSHeapUsedSize` を使ったか

最初はブラウザ標準の `performance.memory.usedJSHeapSize` で計測した。
結果、300行から100万行まですべてのケースで **完全に同じ値
（16,100,000 バイト固定）** が返り、行数によるメモリ増加が一切観測できな
かった。これは Chrome がサイドチャネル攻撃対策として `performance.memory`
の値を粗く丸めている（数MB単位でバケット化し、更新頻度も落としている）
ためで、今回のような小刻みな比較には使えなかった。CDP の
`Performance.getMetrics` が返す `JSHeapUsedSize` はこの丸めを受けず、
行数に応じた実際の増加を観測できたため、これに切り替えた。

（`window.__metrics` 内の `memBaselineBytes` 等のフィールドは
`performance.memory` を使った名残で、この報告では使っていない。
値が全ケースで同一なのはそのため。）

## 行数別の結果（dot）

| 行数 | DuckDB-WASM登録 | 初回描画 | ドラッグ→件数更新 | メモリ(登録+描画直後) | DOMノード数(同) |
|---|---|---|---|---|---|
| 300 | 53.3 ms | 47.8 ms | 169.3 ms | 11.3 MB | 435 |
| 1万 | 68.8 ms | 65.6 ms | 162.2 ms | 13.6 MB | 10,135 |
| 10万 | 116.2 ms | 201.4 ms | 517.9 ms | 28.2 MB | 100,101 |
| 100万 | 574.8 ms | 1,614.3 ms | 6,821.8 ms | 193.3 MB | 1,000,101 |

参考: ブラウザ起動直後（ページ遷移前）の基準値はメモリ 0.5 MB / 8 ノード。
どの行数でもこの基準値から測っている。

DuckDB-WASMへの登録は最後まで律速しない（100万行でも0.6秒未満）。
律速しているのは初回描画とドラッグ応答で、特にドラッグ応答は
10万行で518ms、100万行で6.8秒と、行数に対して非線形に悪化している。

## 100万行での dot / raster / hexbin 比較

| | dot | raster | hexbin |
|---|---|---|---|
| 初回描画 | 1,614.3 ms | 111.2 ms | 327.3〜327.4 ms |
| ドラッグ→件数更新 | 6,821.8 ms | 157.5 ms | 157.5 ms |
| DOMノード数（散布図要素配下） | 1,000,101 | 39 | 351 |
| メモリ（登録+描画直後） | 193.3 MB | 103.5 MB | 96.0 MB |
| メモリ（ドラッグ後） | 126.6 MB | 106.0 MB | 98.5 MB |

dot に対して raster はドラッグ応答が約43倍（6,821.8ms → 157.5ms）、
初回描画が約15倍（1,614.3ms → 111.2ms）速い。hexbin もほぼ同水準。

## 原因: 1点=1DOMノード、その証拠

`dot` マークは Observable Plot の実装上、データ1点につき実DOM要素
（`<circle>` などのSVG要素）を1つ生成する。これを、散布図要素配下の
実DOMノード数（`scatter.querySelectorAll('*').length`）を行数ごとに
比較することで確認した。

| 行数 | dot のDOMノード数 | 行数との差分（軸等のオーバーヘッド） |
|---|---|---|
| 300 | 435 | +135 |
| 1万 | 10,135 | +135 |
| 10万 | 100,101 | +101 |
| 100万 | 1,000,101 | +101 |

行数が10倍・100倍になっても、ノード数の増分はほぼ「行数 + 固定オーバー
ヘッド」の形を保っており、オーバーヘッド自体は行数に依存せず
100〜135ノード程度で一定している（軸・枠・凡例などプロット本体以外の要素と
見られる）。これは dot マークが1行=1DOMノードで実装されていることの
直接的な証拠になっている。

対照として、DuckDB側で集計してから描く raster / hexbin のDOMノード数は
行数に応じて増えていない。

| 行数 | raster | hexbin |
|---|---|---|
| 300 | 51 | 230 |
| 1万 | 37 | 355 |
| 10万 | 39 | 350 |
| 100万 | 39 | 351 |

raster は常時40ノード未満（画像1枚+軸等）、hexbin は300〜360ノード程度
（ビン=ヘキサゴンの数はプロットの表示範囲とビン幅で決まり、行数には
依存しない）で、どちらも行数に対してほぼ一定だった。

## 対策後の結果と、残ったメモリコストの説明

raster / hexbin への切り替えで、初回描画・ドラッグ応答ともに劇的に改善し、
かつ行数を増やしてもほぼ一定のコストに収まることを確認した（前掲の
「100万行での比較」表、および行数別の推移は下記）。

| 行数 | dot 応答時間 | raster 応答時間 | hexbin 応答時間 |
|---|---|---|---|
| 300 | 169.3 ms | 154.8 ms | 157.3 ms |
| 1万 | 162.2 ms | 157.4 ms | 156.8 ms |
| 10万 | 517.9 ms | 157.8 ms | 157.3 ms |
| 100万 | 6,821.8 ms | 157.5 ms | 157.5 ms |

raster / hexbin の応答時間は行数によらずおよそ157〜158msで揃っている。
これはドラッグのたびに走る DuckDB 側の集計クエリの実行時間が支配的で、
集計後のグリッド/ヘキサゴン数（＝描画コスト）が行数に依存しないためだと
考えられる。

**メモリは改善するが、ゼロにはならない。** raster / hexbin は96〜106MB、
dot は193MB（描画直後）で、raster/hexbinの方が明確に少ないものの、
300行のとき（11〜13MB）と比べると依然として大きい。DOMノード数を
固定化してもこの増分が残る理由は、**DuckDB-WASM がテーブル自体
（100万行分のデータ）をメモリ上に保持し続けているコスト**であり、
マーク（描画方法）をどれに変えても元データを保持する以上は避けられない。
これはDOM/描画側のコストとは別の要因で、raster/hexbinへの切り替えでは
解消できない。

## 閾値の根拠と、まだ絞り込めていない点

### 根拠にした事実

- dot のドラッグ応答時間は 1万行162ms → 10万行518ms → 100万行6,822ms と、
  行数に対して非線形に悪化している。
- raster / hexbin はこの同じ範囲でおよそ157〜158msとほぼ一定。
- 一般に「500ms前後から遅延が体感され始める」という目安に照らすと、
  10万行の時点（518ms）で既に境界に達している。

以上から、「行数が10万を超えたあたりから raster/hexbin への切り替えを
検討し、実用上は10万〜100万の間のどこかに明確な閾値がある」という
**定性的な**結論は言える。ただし以下の理由で、これ以上の精度で
「具体的に何行が境界か」を特定することはできていない。

### まだ分かっていないこと

1. **10万〜100万の間を計測していない。** 今回測ったのは300 / 1万 / 10万 /
   100万の4点のみで、この間（例: 30万、50万行）でdotの応答時間がどう
   推移するか（緩やかに悪化するのか、ある行数から急激に跳ね上がるのか）は
   不明。
2. **CDPの`JSHeapUsedSize`がDuckDB-WASMのWASM線形メモリ
   （ArrayBuffer）をどこまで含んでいるかを検証していない。** ブラウザの
   タスクマネージャ等でプロセス全体のメモリと突き合わせていないため、
   OSから見た実際のプロセスメモリがどれだけかは分かっていない。
3. **列数・データ型を変えた場合の挙動は未計測。** 今回のデータは
   x, y, group（数値2列+カテゴリ1列）という単純な構成のみ。列数が増えた
   場合や文字列長が長い場合にどう変わるかは調べていない。
4. **dot マーク自体の高速化オプション（半径を絞る、キャンバス
   レンダラーへの切り替えなど）が mosaic-plot 側にあるかどうかは調べて
   いない。** 今回試した代替は raster / hexbin の2つのみ。
5. **ネットワーク環境やGPU描画パスの違いによる差は未検証。** 測定は
   すべて同一マシン・同一セッション、ブラウザキャッシュなし
  （毎回新規launch）という単一条件下のもの。
6. **hexbin×100万行で1回だけ、全体の所要時間が12.4秒という外れ値が
   出た。** 内訳（CSV生成・DB登録・初回描画の各時間）は他の条件と一致して
   おり、単体で再実行すると1.99秒に収まったため、jsDelivrからの
   DuckDB-WASM本体フェッチが一時的に遅延した計測ノイズと判断し、本文の
   数値には正常値を採用した。ただしこの推測を裏付けるネットワークログ
  （HARなど）までは取得していない。

## 1万〜10万行の再計測（2026-09）

上の計測は技術検証用の最小構成（散布図1枚）で行ったもので、1万〜10万行の間を
測っていなかった。閾値 50,000 はその空白域に安全側で置いた暫定値だったため、
機能がそろった現在のアプリ（散布図＋ヒストグラム2枚、dot は母集団・選択の2層、
統計量・カテゴリ構成などの集計クライアント付き）で改めて測った。

### 測定条件

- **ブラウザ**: Playwright 1.63.0 のヘッドレス Chromium（macOS上）。行数・マークごとに
  ブラウザを新規起動。
- **対象**: 本番ビルド。dot / raster を比べるため、閾値だけを「常に dot」
  「常に raster」に書き換えた2つのビルドを一時的に作った（計測後に元へ戻した）。
- **データ**: 数値2列（相関あり）＋カテゴリ1列、欠測なし。
- **操作**: X 軸のヒストグラム上で、15段階・16ms 間隔のマウス移動によるドラッグを
  範囲を変えて5回。ヒストグラムを動かすと散布図（全点）が描き直されるので、
  dot の描画コストが最も効く操作になる。回帰直線は、ドラッグが止まってから追従する
  集計側（`settle.ts`）に属するので、描画の計測に混ざらないよう表示を切った。
- **指標**:
  - **最長フレーム**: ドラッグ中に観測した long task（50ms 以上メインスレッドを
    占有した処理、`PerformanceObserver`）の最大値。入力に対して画面が止まる時間。
  - **合計停止**: ドラッグ中の long task の合計（約1秒のドラッグ中に止まっていた時間）。
  - **追従遅れ**: マウスを離してから、チャート領域の DOM 変化が収まるまでの時間。
  - いずれも5回の中央値。

### 前回の指標（ドラッグ→件数更新）を使わなかった理由

最初は前回と同じく「マウスを離してから選択件数が更新されるまで」を測ったが、
現在のアプリでは件数は軽いクエリで即時に更新され、ドラッグ中に最終値へ
達してしまうため、離した時点ではもう変化しない。結果は描画の重さと無関係に
30〜500ms の間でばらつき、dot の描画コストを捉えられなかった。そこで、
描画がメインスレッドを止める時間（long task）を直接測る方式に変えた。

### 結果

| 行数 | dot 最長フレーム | dot 合計停止 | dot 追従遅れ | raster 最長フレーム | raster 追従遅れ |
|---|---|---|---|---|---|
| 1万 | 0〜51 ms | 0〜53 ms | 0 ms | 0 ms | 0 ms |
| 1.25万 | 58 ms | 608 ms | 0 ms | — | — |
| 1.5万 | 76 ms | 889 ms | 0 ms | — | — |
| 1.75万 | 80 ms | 1,053 ms | 0 ms | — | — |
| 2万 | 93〜109 ms | 1,209〜1,282 ms | 0 ms | 0 ms | 0 ms |
| 3万 | 142 ms | 1,908 ms | 0 ms | 0 ms | 0 ms |
| 4万 | 207 ms | 2,518 ms | 123 ms | 0 ms | 0 ms |
| 5万 | 278 ms | 2,949 ms | 161 ms | 0 ms | 0 ms |
| 6万 | 277 ms | 3,797 ms | 161 ms | 0 ms | 0 ms |
| 7万 | 461 ms | 4,841 ms | 283 ms | 0 ms | 0 ms |
| 8万 | 440 ms | 4,957 ms | 276 ms | 0 ms | 0 ms |
| 10万 | 607 ms | 7,271 ms | 325 ms | 0 ms | 0 ms |

（1万・2万は2回に分けて測った値の幅。1.25万〜1.75万は dot のみ測った。
「0 ms」は 50ms 以上の long task が1度も出なかったことを表す）

### 閾値を 15,000 にした

- dot の最長フレームは行数にほぼ比例して伸び、2万行前後で 100ms を超える。
  入力への応答が 100ms を超えると遅れとして体感されるという目安に照らすと、
  以前の閾値 50,000 では毎フレーム約 280ms 止まっていたことになる。
- raster は 1万〜10万行を通じて long task が出なかった。
- 100ms を明確に下回った最大の計測点である **15,000** を新しい閾値にした。
  2万行の 93〜109ms は測るたびに 100ms をまたぐので、境界そのものには置かなかった。

前回の技術検証より dot が重く出ているのは、散布図を「母集団（灰）＋選択中（色）」の
2層にしたことで、1行あたりの SVG 要素が増えたためと考えられる（1万行で散布図配下の
ノード数は 15,001。技術検証時の1層では 10,135）。

### この再計測でも分かっていないこと

- **Safari / Firefox、非力な端末での値。** 同一マシンのヘッドレス Chromium のみで測った。
  描画の遅いブラウザ・端末では境界が 15,000 より下がりうる。
- **散布図そのものをドラッグしたときの値。** crossfilter では自分のチャートの選択は
  自分に効かせないため、散布図のドラッグでは散布図は描き直されず、ヒストグラムだけが
  更新される。ここでは最も重い「ヒストグラムを動かす」操作だけを測った。
- **列数が多い場合。** 集計クライアントのクエリは列数に比例して重くなるが、
  集計側はドラッグが止まってから走るので、ここで測った描画の停止には効かないはず、
  という推測までで、確認はしていない。

## 階層クラスタリングの行数の上限（2026-09）

階層クラスタリング（`web/src/hclustPanel.ts`、ライブラリは ml-hclust 4.0.0 の `agnes`）は、
全行どうしの距離を順に結合していくため、行数に対して急に重くなる。上限を超える行数の
ときは無作為に間引いて実行するので、その上限を計測して決めた。

### 目安

「実行」を押してから樹形図とヒートマップが出るまで **2 秒以内**。計算は Web Worker で
行うので画面は固まらないが、結果を待つ時間として 2 秒を超えると「押したのに何も
起きない」と感じやすい、という判断。

### 1. Node.js での計算時間（ライブラリ単体）

数値6列の合成データで、`agnes` だけの時間。Node.js（V8）、同一マシン。
750〜1,250 行は3回の中央値、それ以外は1回。

| 行数 | Ward 法 | 平均連結法 | 完全連結法 |
|---|---|---|---|
| 500 | 0.15 s | 0.20 s | 0.18 s |
| 750 | 0.34 s | 0.52 s | 0.52 s |
| 1,000 | 1.23 s | 1.23 s | 1.23 s |
| 1,250 | 2.46 s | 2.45 s | 2.44 s |
| 1,500 | 4.33 s | 4.55 s | 4.28 s |
| 2,000 | 10.3 s | 10.4 s | 10.4 s |
| 2,500 | 20.9 s | 20.9 s | 20.3 s |

行数が2倍で時間がおよそ8倍、つまり行数のほぼ3乗で増える。この段階では
「1,000 行なら約 1.2 秒」と見て、上限を 1,000 行にしていた。

### 2. 実際のアプリでの時間（3ブラウザ）

本番ビルドをヘッドレスブラウザで開き、サンプルデータ（3,000 行、欠測の無い行 2,682 行、
数値6列）で「実行」を押してから、樹形図が出て「実行」ボタンが再び押せるようになるまでの
時間。行データの取り出し・Worker との受け渡し・描画を含む。上限だけを書き換えた
ビルドを一時的に作り、上限ちょうどの行数で測った。各3回の中央値。

| 上限（= 実行した行数） | ブラウザ | Ward 法 | 平均連結法 | 完全連結法 |
|---|---|---|---|---|
| 800 | Chromium | 0.72 s | 0.91 s | 0.92 s |
| 800 | WebKit | 0.88 s | 0.82 s | 0.84 s |
| 800 | Firefox | 0.95 s | 0.99 s | 0.91 s |
| 900 | Chromium | 1.06 s | 1.12 s | 1.17 s |
| 900 | WebKit | 1.08 s | 1.06 s | 1.16 s |
| 900 | Firefox | **2.41 s** | 1.32 s | 1.33 s |
| 1,000 | Chromium | 1.24 s | 1.52 s | 1.52 s |
| 1,000 | WebKit | 1.41 s | 1.36 s | 1.42 s |
| 1,000 | Firefox | **2.69 s** | **2.46 s** | **2.20 s** |

（計算だけの時間は画面の状態表示「計算 ○ 秒」にも出している。Firefox の 900 行の
Ward 法は3回で 1.16 / 2.15 / 2.63 秒とばらつきが大きかった）

### 上限を 800 行にした

- 1,000 行では Firefox がすべての連結法で 2 秒を超えた。Node.js の計測だけで決めた
  1,000 行は、ブラウザによっては目安を満たしていなかった。
- 900 行でも Firefox の Ward 法（初期値）が 2 秒を超えた。
- 800 行は 3ブラウザ × 3連結法のすべてで 1 秒前後に収まる。
- よって、どのブラウザでも目安を明確に満たす **800 行** を上限にした。
  上限を超えたときは、何件から何件に減らしたかを画面に表示する。
  間引きは `ORDER BY hash(rowid)` で、同じ条件なら同じ行が選ばれる（結果が再現する）。

### まだ分かっていないこと

- **列数を変えた場合。** 計測は数値6列のみ。距離の計算は列数に比例するが、結合の
  手順（行数の3乗）が支配的なので、上限への影響は小さいと見ている（未確認）。
- **Firefox が 800〜900 行の間で急に遅くなる理由。** ガベージコレクションなどが
  疑わしいが、プロファイルは取っていない。
- **ヘッドレスではない実機のブラウザ・非力な端末での値。**

## 統計用グラフの描画について（2026-09、記録のみ）

- 散布図行列は、点表示と密度表示（raster）の切り替えを「行数 × 対角以外のマスの数」
  （= 1回の選択で描き直す点の総数）で判定している。閾値は散布図と同じ 15,000。
  サンプルデータ（3,000 行・5列 = 20マス）では 60,000 となり raster になる。
  この扱いの妥当性（マスが小さいと1点あたりの描画コストが下がる可能性）は測っていない。
- Q-Q プロットは行数によらず 100 個の分位点だけを描くので、描画の重さは行数に依存しない。
- 相関行列・バイオリン図は集計済みの数十〜数百の値だけを描く。

## 再現方法

計測に使った Playwright のスクリプトは使い捨てで、コミットには含めていない。

- **技術検証時（前半の表）**: 当時の `web/src/main.ts` には `?n=<行数>&mark=<dot|raster|hexbin>`
  で行数とマークを切り替える仕組みがあった（現在は削除済み。`git log` で当時の版を参照）。
- **階層クラスタリングの上限**: Node.js では ml-hclust の `agnes` を直接呼んで時間を測った。
  アプリでの時間は、`web/src/hclustPanel.ts` の `MAX_HCLUST_ROWS` だけを書き換えた
  ビルドを `vite build --outDir` で作り、Playwright で「実行」から状態表示に
  「計算 ○ 秒」が出るまでを測った。
- **1万〜10万行の再計測**: `web/src/charts.ts` の `DOT_TO_RASTER_THRESHOLD` を
  一時的に `Infinity`（常に dot）/ `0`（常に raster）に書き換えて `vite build --outDir` で
  別々にビルドし、`vite preview` で配信したページに CSV を読み込ませ、
  ドラッグ中の `PerformanceObserver`（`longtask`）と `#plots` の `MutationObserver` で測る。
