# Brushlink

実験データをドラッグ選択するだけで、条件ごとの違いをその場で比較できる探索的データ分析ツール。

![デモ](docs/demo.gif)

*(名前は可視化分野の用語 brushing and linking から。TIBCO Spotfire に着想を得ているが、製品名としての言及ではなく出典として記す)*

## 解決する課題

研究室の実験は、条件を変えながら同じ計測を何十回も繰り返す。培養条件ごとの温度・収率、
分析条件ごとの吸光度・ノイズ――出てくる CSV / Excel は増える一方で、「条件Aと条件Bで
何が違うか」を見るたびに、Excel でピボットテーブルを組み直したり、条件列でシートを
フィルタしてはグラフを取り直したりする作業が発生する。データ自体はシンプルでも、
比較のたびに手作業が挟まるので、確認のサイクルが遅くなる。

このツールが直接手当てするのはそこで、散布図の上をドラッグして範囲を選ぶだけで、
その範囲に対応する行がヒストグラム・統計量・データ表・回帰結果に即座に反映される。
ピボットテーブルを作り直す代わりに、見たい範囲を目で選ぶだけで比較が完了する。
ヘッダ行がずれた実験機器の出力や、欠測を含むデータもそのまま投げ込めるようにしてあるのは、
研究室のデータが「素直な整形済み CSV」ではないことが多いという前提に立っているため。

## 使い方

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
panel serve app.py --show
```

ブラウザが開いたら、画面上部のドロップ領域に CSV / Excel(.xlsx) をドラッグ＆ドロップする。
先頭数行がそのままプレビューされるので、ヘッダの行をクリックして選ぶ
（文字列の行の次に数値中心の行が続く箇所を自動推定して初期選択してあるので、
素直な CSV ならクリック不要でそのまま読み込まれる）。あとは散布図をドラッグするだけ。

- サイドバーのフィルタで母集団そのものを絞り込み、その中で選択する（2 段構え）
- 動作確認だけしたい場合は `python tests/smoke_test.py`（ブラウザ不要）

## 技術構成

| 層 | 実装 | 役割 |
|---|---|---|
| データ | DuckDB + pandas | インメモリ列指向エンジン。CSV / Parquet / Excel を SQL で扱う |
| 可視化 | HoloViews + hvPlot | `link_selections` によるチャート間の選択連動 |
| UI | Panel | ウィジェット・レイアウト・配信 |
| 統計 | R (rpy2、任意) | 選択範囲に対するモデル当て。未インストールなら numpy に自動フォールバック |

```
app.py              アプリ本体（ウィジェットとレイアウトの組み立て）
src/data.py         DuckDB への読み込み・列メタ情報の推定・アップロード処理
src/charts.py       チャート生成と選択連動
src/filters.py      フィルタパネルの生成と母集団の絞り込み
src/r_bridge.py     R 連携（R 不在時は numpy にフォールバック）
tests/smoke_test.py 連動と回帰が通ることの検証
```

## 設計判断とその理由

**Streamlit ではなく Panel を選んだ**
Streamlit はスクリプト全体を毎回再実行するモデルで、状態はセッション変数として
明示的に持ち回す必要がある。クロスフィルタは「どこかで選んだ範囲」を他のすべての
コンポーネントが参照し続ける必要があり、再実行のたびに状態を手で復元するのは
本質的に相性が悪い。Panel は HoloViews の `link_selections` がウィジェットの
パラメータとして選択状態を保持するため、この種の相互参照をフレームワーク側に
任せられる。

**公開デプロイをしない**
このツールが扱う対象は研究室の実験データで、公開サーバーに上げること自体が
データの持ち出しになりかねない。ローカルで完結させ、外部サーバーへ研究データを
送らないことを前提にしている。ポートフォリオとしての見せ方も、常時稼働のデモより
「手元で動かせば同じものが見える」ことを優先している。

**カーディナリティの閾値を 20 にした**
チェックボックスや色分けの選択肢として成立するカテゴリ列の上限を、Bokeh の既定
カテゴリパレット Category20 が持つ色数（20）に合わせた。これを超える列（ID 列や
日付列など、ほぼ全行ユニークな列）を色分けに使っても色は循環して区別できなくなり、
チェックボックスも縦に伸びて一覧性を失う。恣意的な数値ではなく、実際に UI が
機能しなくなる閾値から逆算した。

**重い依存はオプション化し、無くても動く状態を維持する**
R（rpy2）は現状の必須要件ではなく、入っていれば `lm()` による回帰と p 値が使え、
入っていなければ numpy による代替の回帰に自動で切り替わる。この「無ければ簡易版に
落ちるだけで、アプリ自体は止まらない」という方針は、今後追加予定の UMAP（重い依存の
`umap-learn` が無ければ PCA のみ提示）や、大規模データ用の Datashader にも同じ形で
踏襲する。ポートフォリオを見る人の環境に、重量級のライブラリが揃っている保証はない。

## 実装中に見つけた不具合

**欠測を含む行が、フィルタ未操作の初期状態で消えていた**
症状: 生存率などの数値列に欠測（NaN）が含まれるデータをアップロードすると、
フィルタを一切操作していないのに該当行だけ統計量・データ表から消えていた。
原因: `pandas.Series.between()` と `.isin()` はどちらも NaN に対して `False` を
返すため、レンジフィルタ・チェックボックスフィルタのマスクが暗黙のうちに欠測行を
弾いていた。「初期状態は全件を通す」という設計を、実データで検証して初めて破って
いることに気づいた。
対処: 欠測値は判定不能として無条件に通すよう、各マスクに `| 列.isna()` を足した。

**アップロードで列構成が変わった直後、KeyError で描画が落ちることがあった**
症状: 列構成の異なるファイルに読み替えた直後、X軸・Y軸のセレクタを新しい列名に
更新する処理の途中でチャートが例外を出すことがあった。
原因: X軸・Y軸・色分けの3つのウィジェットを1つずつ順に更新すると、「Xだけ新しい
列・Yはまだ古い列」という中間状態でチャートの再描画が同期的に走ってしまい、古い
列名が新データに存在せず落ちていた。
対処: `param.parameterized.batch_call_watchers` で3ウィジェットの変更通知を
ブロックの終わりまでまとめ、すべて更新し終えてから1回だけ再描画されるようにした。
